# 游戏开发工作链

## 1. 先确定体验和视觉方向

用一句话说明玩家在做什么、最有趣的反复行为是什么，再选择少量能够互相影响的系统。建立视觉参考：年代、地域、轮廓、色彩、材质、光照、相机、人物比例、UI 密度。概念图指导制作；实际游戏画面决定是否采用。

创作可以自主试验。遇到会改变作品方向的选择再交给人判断；不要用过多限制替代设计判断。

## 2. 检索成熟素材与决定原创部分

通过 `find_assets.py` 检索素材目录；从 Fab/Epic、Asset Store、Poly Haven、Mixamo 等来源按实际需要选择。拥有、下载、导入、视觉合格是不同状态。

逐项记录来源、许可证、允许用途、格式、尺度、轴向、枢轴、纹理、依赖、哈希和项目用途。UE 文件格式与 UE-only 授权分别判断。带有生成式 AI 输入限制的素材不送入生成模型；普通导入和摆放按取得的授权处理。

## 3. GPT 图片与原创模型

GPT 内置图像生成是主路线；保存原图、提示词、提供方、分辨率、哈希和检查笔记。项目内使用独立文件名。ComfyUI 作为可选本地备选，明确启用后才运行，输出不覆盖 GPT 原图。

原创形体可比较 Hunyuan3D-2 full、Mini 与其他建模方式。当前工作台的 shell 案例选用了 full，但这不构成所有模型都应采用它的规则。角色优先考虑适合制作的拓扑和骨架；生成网格不自动等于合格角色。

## 4. Blender 整理

保留输入与失败候选。检查连通组件、拓扑、法线、UV、材质、尺寸、枢轴、三角面数量。角色增加骨架、权重、动作和关键姿态变形检查。导出后重新导入，拍摄多视角并与参考比较。Blender 精修不会解除上游素材的限制。

## 5. Unity / Unreal 集成

使用独立验证工程，避免覆盖正在制作的游戏。多 Editor 并存时显式指定项目路径，并在变更前核对 `Application.dataPath`。验证工程选 URP；过去在该工程 D3D11 渲染请求路径发现 GPU Resident Drawer 材质问题，关闭它的记录仅属于该验证案例。

导入后验证模型、材质、动作、碰撞与真实玩法中的用途。Editor 编译、CPU 数据检查和截图文件存在都不足以证明实际渲染成功。

UE5 使用独立 `UnrealProject` 和编辑器 Python 适配，构建接 UAT，测试接 Automation。共用资产需分别检查单位、坐标、材质和动画；引擎内的运行验证记录分别保存。UE5 NullRHI 场景检查只证明数据链路，后续仍需真实渲染和打包游戏体验。

## 6. 构建与实际运行

先检查构建结果及警告，再用真实 Windows 包运行 QA。保存进程退出码、运行报告、完整构建文件哈希和非空 GPU 画面。观察动画是否随时间变化、蒙皮是否变形、碰撞是否生效、贴图是否真的进入画面。验证脚本只管理自己启动并记录的进程。

## 7. 人工体验与迭代

用正常输入试玩：操作手感、镜头、节奏、可读性、音画反馈、系统联动、失败补救、存读档和性能。检查结果指导下一轮设计。工具运行通过、自动测试通过与完整成品验收分别报告。

## 8. 版本与交接

源码和配置进 Git；大体积、可分发的自有资产可按项目需要进入 LFS。账号、本机配置、模型权重、缓存、构建、原始受限资源不进入公开仓库。交接记录写清已做、验证方式、实际采用版本、已知限制和下一步；不把候选或局部检查当成默认成品。
